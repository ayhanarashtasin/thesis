# Implementation and Experimental Setup {#chap:impl}

This chapter describes how the methodology was implemented: the software architecture, data collection and preprocessing, rewards and the code sandbox, the policy and GRPO trainer, the direct HLoRA-to-RL baseline, evaluation, checkpointing, and validation. It ends with the configuration of the GPU pilots and the implementation status of every phase.

## System Architecture and Software Design {#sec:software}

The platform is a Python 3.11 package, rahc_lora, with a single command-line interface (doctor, prepare-data, train) and typed Hydra configuration. The code follows a strict layered architecture ({fig:fig_5_1_software_layers}). The interface layer only parses configuration and calls package functions. The orchestration layer (the ContinualTrainer, checkpointing, and run artifacts) coordinates components without implementing scientific logic. The domain layer contains the RL objective, consolidation, and evaluation. The adapter layer wraps models, tasks, and rewards, and the infrastructure layer provides validated configuration, atomic file writes, structured logging, manifests, and reproducibility utilities. Dependencies point downward only. Scientific logic such as losses, answer parsing, and forgetting metrics never lives in scripts or notebooks.

[[FIG:fig_5_1_software_layers]] Layered software architecture of the rahc_lora package.

Configuration is composed by Hydra from groups (model, task, method, task stream, experiment, rollout, optimizer, scheduler, checkpoint, launcher, and sandbox). It is validated into immutable dataclasses and frozen when a run starts. Validation enforces, for example, that the standard method rl_lora enables no retention component, that model revisions are 40-character commit hashes, and that a requested precision is supported, with no silent fallback. The resolved configuration and its SHA-256 hash are saved with every run and checkpoint.

## Data Collection and Preprocessing {#sec:data}

### Data sources

The continual-RL stream uses four task families, and the capability suite uses five evaluation-only datasets, all pinned to exact Hugging Face revisions ({tab:tab_5_1_datasets}). GSM8K [@cobbe2021gsm8k] provides grade-school math word problems with numeric answers. ARC-Challenge [@clark2018arc] provides grade-school science questions with three to five labelled options. MBPP [@austin2021mbpp], sanitized version, provides Python programming problems with hidden assert-based tests. The custom verifiable-constraints dataset is generated by the project.

[[TAB:tab_5_1_datasets]]

### Data cleaning and split construction

Raw records are never modified or committed. Each record receives a stable identifier, the SHA-256 hash of configured immutable identity fields (for example the GSM8K question text or the ARC item ID). Source training records are ranked by the SHA-256 of "split_seed:example_id". This makes role assignment independent of the order in which the provider returns records. Official splits are preserved where they exist. GSM8K has no validation split, so validation (10%) and anchor candidates (10%) are taken from the ranked source training split, and the official test split is the held-out test. ARC-Challenge and MBPP keep their official validation and test splits, and anchor candidates (10%) are removed from the source training split. Every trainable manifest rejects duplicate IDs and duplicate content hashes across roles, and empty roles fail loudly ({fig:fig_5_2_data_isolation}).

[[FIG:fig_5_2_data_isolation]] Data roles and isolation. Split sizes of the four RL tasks and the evaluation-only suite, with the flows each role is allowed to feed.

### Data transformation: prompts and answer formats

Each task formats a fixed, versioned prompt. GSM8K uses "Solve the problem. Give your final numeric answer clearly." followed by the problem. ARC-Challenge uses "Choose the correct option and end with its label." followed by the question and labelled options. MBPP uses "Write a complete Python solution. Return only Python code; do not include tests." followed by the problem; the tests are hidden from the prompt. The capability suite uses "Select the best completion and answer with its label." for MMLU, HellaSwag, and ARC-Easy, and the official IFEval prompts unchanged. Prompts are tokenized with the pinned tokenizer and truncated to 128 tokens.

### Custom verifiable-constraint dataset

Official IFEval must remain evaluation-only, so the constraint task uses a separate, generated dataset (version 1.0.0, seed 20260922) of 80 prompts from eight template families. The families are separated by role: topic-keyword-bullets and brief-forbidden-ending for training; summary-sections and JSON-profile for validation; steps-keyword and note-word-range for anchor candidates; and recommendation-bullets and JSON-inventory for test. Constraints include an exact bullet count, keyword counts, forbidden words, required ending phrases, word-count intervals, titled sections, and valid JSON with required fields. The reward is the fraction of constraints satisfied. Before manifests are written, every custom prompt is compared with the 541 official IFEval prompts by exact and aggressively normalized text. The checked-in audit reports zero exact and zero normalized overlaps. Any overlap would abort data preparation.

### Summary of preprocessed data

Preparation writes only JSON manifests and the overlap audit. Each manifest records the canonical source, revision, license and citation, source-split mapping, preprocessing, prompt and reward versions, exact role membership IDs, content hashes, and per-example provenance. The run manifest of every GPU run records the SHA-256 fingerprint of each dataset manifest, so any change to the data protocol produces a visibly different run identity.

## Rewards and Isolated Code Execution {#sec:rewards}

All rewards are deterministic functions with a documented range of [0, 1]. Malformed or ambiguous answers receive a documented score of zero rather than a guessed interpretation. The numeric scorer extracts the final number after an explicit marker ("####", "final answer", or "answer") or, failing that, the last number in the response. It converts the number to an exact rational, handling thousands separators, currency symbols, fractions, and percentages, and compares it exactly with the reference. The multiple-choice scorer accepts one unambiguous label after a marker such as "answer:", a bare label, or an exact normalized option text. It rejects responses that name two different labels. Unit tests cover hand-written accepted, rejected, malformed, and normalization-equivalent examples for every scorer.

Generated code is executed only through an isolated Docker runner ({fig:fig_5_3_code_sandbox}). Each response is written with its hidden tests into a read-only workspace. It runs in a new container from a digest-pinned image with no network, a read-only root file system, all capabilities dropped, no-new-privileges, user 65534, 256 MB of memory with no additional swap, one CPU, 32 processes, CPU-time and file-descriptor limits, a 5-second timeout, and a 64 KiB output cap. The container is removed afterwards. Only the test outcome leaves the sandbox. If the Docker daemon is unavailable, scoring raises an error: there is no host-execution fallback.

[[FIG:fig_5_3_code_sandbox]] Security boundary for code rewards. Generated code runs only in an ephemeral, network-disabled, resource-limited container, and only the test outcome leaves it.

## Policy, Rollouts, and the GRPO Trainer {#sec:trainer}

The model factory loads the pinned causal LM (Qwen2.5-0.5B-Instruct or Qwen2.5-1.5B-Instruct [@qwen2024]) in explicit BF16 with remote code disabled. It freezes every backbone parameter and attaches exactly one PEFT LoRA adapter (rank 8, α = 16, dropout 0) to the q, k, v, and o projections of every layer. For Qwen2.5-1.5B this gives 2,179,072 trainable parameters. The same closed-form count reproduces the 1,081,344 trainable parameters that the factory reported when loading Qwen2.5-0.5B on CUDA. Only LoRA tensors enter the AdamW optimizer [@loshchilov2019], and the adapter is never reset between tasks. A CPU-only tiny model with a byte-level tokenizer shares the same policy interface and is used for deterministic tests.

Each update samples two training prompts by deterministic cycling through the current task's training split. It draws G = 4 responses per prompt with temperature 1.0, top-p 1.0, and at most 128 new tokens, storing the old log-probability of every generated token. Rewards are then normalized within each group in FP32 using the population standard deviation. Groups with a standard deviation at or below 10⁻⁸ receive exactly zero advantage, and advantages are clipped to ±5. The token-mean clipped surrogate (ε = 0.2) is optimized with one AdamW step per rollout, a learning rate of 10⁻⁴, and gradient-norm clipping at 1.0. Rewards, advantages, loss, and gradients are checked for finiteness before the optimizer is allowed to change any parameter. These semantics, which libraries leave open, are fixed in a decision record so that a dependency upgrade cannot change the objective.

Each update logs raw and normalized reward statistics, the number of zero-variance groups, the advantage and ratio clipping fractions, the gradient norm and whether it was clipped, the sampled policy KL (the mean of the old minus new log-probability, a diagnostic of step size), response length and distinct-response fraction, and reward diagnostics. The diagnostics separate parse failures from executed code that failed tests, timeouts, output-limit events, and non-zero exits. System metrics record step time, tokens per second, process memory, and peak GPU allocation.

## Direct HLoRA-to-RL Implementation {#sec:hlora_impl}

The direct HLoRA-to-RL baseline (method hlora_rl) is the Phase 3 reference for consolidation. It transfers the HLoRA idea of element-wise importance with layer coefficients [@song2025hlora] to the shared RL trainer, with two corrections required by RL: importance uses the gradient of the real RL loss, and it uses the movement actually produced by AdamW ({fig:fig_5_4_hlora_rl_implementation}).

During each update, forward hooks on every LoRA target layer capture the input activation (after the configured dropout) and the output gradient. From these the dense effective-weight gradient G_{l} is formed for the forward pass, without reconstructing it from factor gradients. The checkpoint stores the reference LoRA factors, the dense importance, and the layer coefficients. Reference effective updates are recomputed from the stored factors. Unit tests check that zero movement gives a zero path contribution, that the penalty against a reference matches a direct computation, and that the state survives serialization exactly. As Chapter 6 shows, this baseline behaves exactly like RL-LoRA on the first task, as required. It also reveals a weakness of the softmax coefficients, which is the main design lesson of P2.

## Evaluation Implementation {#sec:eval_impl}

At each task boundary, the evaluator generates greedy responses (at most 64 new tokens) for the held-out test examples of every learned task. It scores them with the task's reward and writes one row of the performance matrix together with per-example records. The records contain example IDs, prompt and response hashes, rewards, and parse status, not raw text. Continual metrics are computed only from a complete matrix. Forward transfer is reported as unavailable unless the corresponding pre-learning cells were evaluated.

The capability suite is evaluated once on the frozen starting policy and after every task, and each score is stored with its signed change from the frozen baseline. IFEval is scored with the official Google Research implementation checked out at a pinned commit. Its four runtime source files and the NLTK punkt_tab resource are verified by digest before use, and there is no approximate fallback scorer. MMLU uses a fixed subset of four subjects (abstract algebra, college computer science, high-school physics, professional medicine). MMLU, HellaSwag, and ARC-Easy are scored by exact option label with the same parser as the training tasks, and perplexity is computed on non-empty WikiText-2 test records truncated to 256 tokens. The pilots evaluate the first 64 or 128 examples of each split and capability, as configured.

## Checkpointing, Artifacts, and Reproducibility {#sec:checkpoint}

Every run writes a fixed artifact layout ({fig:fig_5_5_artifact_contract}): the resolved configuration, a schema-validated run manifest (model and tokenizer revisions, command overrides, dependency versions, hardware, and Git state when available), dataset fingerprints, structured learning and system metrics, evaluation records, the performance matrix, capability scores, layer diagnostics, the memory and checkpoint manifests, and a final summary. Checkpoints are written at every task boundary into a new directory, with the size and SHA-256 hash of every file recorded in a manifest. The latest-checkpoint pointer changes only after validation and atomic replacement succeed, and no valid checkpoint is ever overwritten. A checkpoint contains the adapter, optimizer, scheduler, task and step counters, the rollout counter and policy version, the general and rollout RNG states, the performance matrix, the capability history, and the retention state (empty for RL-LoRA, and reference factors, importance, and layer coefficients for HLoRA-RL). Resume rejects any change to the scientific configuration, the model identity, the data fingerprints, or the dependency versions.

[[FIG:fig_5_5_artifact_contract]] Run artifacts and checkpoint contract.

This design proved its value during P2. The 1,000-update MBPP → GSM8K pilot stopped after 918 updates, during GSM8K. Its only resumable checkpoint was the verified task-1 boundary at step 500. A recovery run restored that checkpoint under the identical configuration hash, replayed the remaining 500 GSM8K updates, and completed the final evaluation. Both the source and the recovered checkpoints pass file-membership, size, and hash validation, and the recovery provenance is recorded alongside the artifacts.

## Experimental Setup {#sec:setup}

All GPU pilots share the configuration in {tab:tab_5_2_experimental_configuration}. The stream design proceeded in two stages. Phase 2 tested standard RL-LoRA on the pre-registered order_1 (GSM8K → ARC-Challenge) and order_2 (MBPP → GSM8K) streams at 100 and 500 updates per task, to find out whether the baseline forgets. Because the first task was learned only weakly in these streams (Chapter 6), a stream with a strong first task, ARC-Challenge → GSM8K ("order_arc_first"), was then used to compare RL-LoRA and HLoRA-RL at 100 and 150 updates per task. Runs were executed back to back with identical seeds and settings. {tab:tab_5_3_run_inventory} lists every analysed run.

[[TAB:tab_5_2_experimental_configuration]]

[[TAB:tab_5_3_run_inventory]]

Two deviations from the initial pilot plan were made using training rollouts only and are documented. First, the training response budget was raised from 32 to 128 tokens after probes at 32 and 64 tokens produced no GSM8K reward. Second, the budget was extended from 100 to 500 updates per task after the 1.5B confirmation pilot showed positive GSM8K reward in only 28 of 100 training batches. Held-out scores were not used to choose either setting.

## Validation and Testing {#sec:validation}

Following the rule "cheap validation before expensive validation", the platform was validated before any GPU run and re-validated afterwards ({tab:tab_5_4_validation}). The test suite contains unit tests for splits and manifests, rewards, the constraint generator and IFEval overlap, the sandbox command, GRPO advantages and loss, continual metrics, the capability suite, the official IFEval adapter, and HLoRA importance, together with integration tests for data preparation, mock two-task evaluation, and interrupted training with resume. At the time of writing all 59 tests pass in 12.5 seconds on CPU.

## Implementation Status {#sec:status}

{tab:tab_5_5_phase_status} summarizes the status of each phase, established from repository evidence rather than from file names. Phases 0-2 are complete. Phase 3 is partly complete: the dense HLoRA-to-RL baseline is implemented and has been piloted, but the separate supervised HLoRA reproduction on SciQ, PiQA, MedMCQA, and a Pile subset has not yet been run. Phases 4-7, the RAHC-LoRA components specified in Chapter 4, have not been started. Their configuration switches exist and are validated, but the trainer currently accepts only the rl_lora and hlora_rl methods. It rejects the others explicitly, so no result in this thesis could come from an unimplemented component.
